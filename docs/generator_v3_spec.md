# Спецификация датасета v3: черновик

Дата: 2026-11-06. Статус: **черновик**, решения автора 06.11.2026 внесены (ниже), состав новых схем - после консультации с научным руководителем. Состав и доли - после Gemma 4 E4B и YandexGPT 5 Lite (stage2_plan, фаза 3): правки должны опираться не на одно семейство моделей. Генерацию v3 не начинать до решений автора (раздел 6).
Основа: docs/generator_v2_spec.md (v2 заморожен и не меняется), docs/error_analysis.md (разбор ошибок 4B), docs/stage2_plan.md (C01, GLM), docs/human_test.md (запросы DeepSeek и Kimi).

## Решения автора (06.11.2026)

1. v3, скорее всего, финальная версия датасета. Если правка почти наверняка повышает точность, сравнимость с выборками v2 вторична (касается В1, В2 и раздела 5).
2. Добавлять новые схемы допустимо; какие - после консультации с научным руководителем (В3).
3. Одно из главных требований - совместимость с MC12: каждая схема v3 запускается в MC12 и строится в .CIR (раздел 5).
4. Противоречивые названия: ориентир - элементы, их соединения и номиналы; пользователю можно показывать замечание о расхождении (В5, П7).
5. Имена узлов: использовать в эталоне те имена узлов, что даны в запросе (П1).

## 1. Принцип

v3 = v2 + точечные добавки по найденным причинам ошибок. Формат ответа, канон, оценка (S0-S4, `curve`), отказы, номиналы и семейства v2 не меняются, чтобы разница v2 - v3 объяснялась только составом данных. Каталог `data/dataset/v3`, версия `gen-3`; `generate_v2.py` и выборки v2 остаются воспроизводимыми.

**Имена узлов (П1), проверено 06.11.2026.** Разбор ответа (`canon.parse_netlist`) принимает любые имена узлов, сравнение идёт по изоморфизму, поэтому оценка не меняется. Программа (`app.run`) перед MC12 и .CIR канонизирует схему: узлы становятся `N1…`. Проверка на эталоне `twin_t_notch` (mc12_real) с узлами A-E вместо `N1-N5`: `app.run` - канонический нетлист тот же, MC12 выполнил, .CIR построен; прямой прогон в MC12 без канонизации - файл .ANO тот же, кроме заголовка. Ограничения для генератора: имя узла не совпадает с именем элемента (на узле `R1` при резисторе `R1` MC12 пишет «Part and node have the same name» - схема считается, но это лишнее предупреждение); `0` и `GND` - только земля; `IN` и `OUT` зарезервированы. В v2 буквенный узел `C` в запросе встречается (mc12_real) - разрешён, если элемента `C` нет (элементы всегда с номером: `C1`).

Длинные каскады L3 (8 ошибок на test v2, 16/24) отдельно не добавляются: П1-П3 тренируют то же умение (несколько открытых узлов); проверить на v3.

## 4. Что не лечится данными v3

- **Невиданные названные топологии (A′).** gen_topology A′ - 0 из 50 у 4B и 2 из 50 у GLM: устройство схемы, которой не было в train, модель не знает. Лечится только добавлением топологий в train (вопрос В1); в работе - ограничение: модель понимает описанные соединения, а названные схемы - только из своего каталога.
- **Опечатки, меняющие смысл** («делтиель» прочитан как ОУ-схема): правки текста v2 их уже содержат; разбирать по llm_test.

## 5. Выборки и честность сравнения

- Совместимость с MC12 (решение автора 06.11.2026): допуск в датасет, как в v2, - прогон MC12 и сверка с узловым расчётом; дополнительно каждая схема должна строиться в .CIR (`spice2cir.build`), чтобы программа могла открыть её в MC12. Схема, не прошедшая одну из проверок, в датасет не входит.
- Объём: train 2000 (сравнение с v2 при равном объёме) и 3000 вложенно, как в v2.
- Из train v3 исключаются схемы `llm_test` (D01), `llm_test2` (D02) и `mc12_real` по `circuit_id`.
- **Что меряет разницу v2 - v3.** Правки v3 выбраны по ошибкам на test v2, `gen_*`, `mc12_real` и C01; для сравнения v2 и v3 эти выборки теперь - разработочные: улучшение на них ожидаемо и доказательством не является. Честная мера - выборки, не использованные при выборе правок: `llm_test` (D01, заморожен до обучения, ни одна модель его ещё не видела), новый test v3 (те же генераторы, другие схемы) и `llm_test2`, если её содержание не влияет на v3 (вопрос В3). В работе это записать прямо. Сравнимость вторична (решение автора 06.11.2026), но одна чистая мера нужна, чтобы утверждать «v3 лучше v2»: для этого достаточно `llm_test` (D01) - его состав v3 не трогает.
- `gen_topology` и `gen_family` v2 сохраняются для сравнения; в v3 - свои отложенные топологии и семейство, если В1 и В2 решатся в пользу переноса в train.

## 6. Вопросы к автору

- **В1. Отложенные топологии.** `khn`, `twin_t`, `mfb_hp` отложены в v2 ради проверки переноса (gen_topology); переноса нет (0 из 50). По решению автора 06.11.2026 (точность важнее сравнимости) - перенести в train v3. Открыто: нужна ли v3 своя отложенная топология для главы о переносе (например, Tow-Thomas 2 из дизайнера) или вывод v2 «переноса нет» достаточен.
- **В2. Семейство `path`.** Отложено в v2 (gen_family), 84% против 96% у своих семейств. Так же - перенести в train v3; открыто то же, что в В1.
- **В3. llm_test2 и круг схем Kimi.** Kimi описывал схемы, которых нет в v2: мост Вина, интегратор Дебу, всепропускающий, Т-образная ОС, скорректированный делитель, мостовое Т. Добавить их в v3 - значит выбрать состав по тестовой выборке: llm_test2 тогда меряет только перенос формулировок, не охват схем. Варианты: не добавлять (llm_test2 остаётся чистой); добавить и честно это записать; добавить только те, что есть в учебниках и каталоге MC12 независимо от Kimi.
- **В3 (решение автора 06.11.2026):** добавлять допустимо; состав - после консультации с научным руководителем.
- **В4. Буквы-узлы.** Решено вместе с П1: имена из запроса сохраняются, буква `C` как узел разрешена (элементы всегда с номером).
- **В5. Противоречивые названия (решение автора 06.11.2026).** Эталон - по соединениям и номиналам. Замечание пользователю - в программе: `app.circuit_notes` сравнивает тип, названный в запросе (ФНЧ, ФВЧ, полосовой, режекторный - словарь `roles_ru.json`, как у baseline), с типом по измерению MC12 (`measure`), и при расхождении пишет: «в запросе назван ФВЧ, по описанным соединениям получился ФНЧ». Ответ модели не меняется (только нетлист). Это работа этапа 3, к датасету не относится.
- **В6. Когда.** После Gemma и YandexGPT (разбор их ошибок - в docs/error_analysis.md) и после заморозки llm_test2. Объём работы - около 2-3 дней: генераторы есть, правки - в `compose.py`, `prompts_v2.py`, `describe_ru.py`.
