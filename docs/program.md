# Программа: запрос → нетлист → MC12, сменные переводчики («батарейки»)

Дата: 2026-10-25. Код: `src/mcnl/app.py`, `src/mcnl/translators/`, `src/mcnl/evaluate.py`.

Обновлено 16.11.2026: окно программы - `gui.py` (docs/gui_spec.md, запуск `run_gui.bat`); переводчик по умолчанию - Qwen3.5-4B с адаптером LoRA (`translators/hf_model.py`, окружение `..env-hf`, параметр `trained_on` - на чём обучен адаптер); режим 2 (подбор номиналов, `synth.py`) в программу ещё не подключён. Реальный ОУ на чертеже - `--opamp TL071C` (docs/gui_spec.md, «Реальный ОУ»). Режим 2 (подбор номиналов) - основа встроена 16.11.2026: `--mode 2`, docs/mode2_spec.md, раздел 9. Запросы, которые программа показывает пользователю, - выборка program (`program_prompts.py`): новая модель проходит её на 100% (docs/stage2_plan.md, «Сводка»).

## Конвейер (`app.py`)

```
запрос на русском
  → переводчик (батарейка: baseline / обученная модель)      → строки элементов или JSON-IR
  → [режим 2] ответ с ? и .SPEC → synth.run: номиналы из рядов → дальше как подобранная схема
  → разбор и канон (score.parse_output, canon)                → S0
  → характерная частота: узловой расчёт mna.py на 1 Гц - 100 МГц (эталона у пользователя нет; у интегратора
    и дифференциатора - частота единичного усиления)
  → [--opamp] насыщение реального ОУ по постоянному току (mna.saturation): есть - на чертеже идеальный ОУ и замечание
  → схема .CIR (spice2cir; с --opamp - реальный ОУ и питание ±15 В)
  → расчёт в MC12: обвязка bench (AC, ±3 декады) → S1, измерения measure.py; с реальным ОУ тем же запуском - сам чертёж
  → по флагу --open открыть .CIR в MC12
```

```
python src/mcnl/app.py "RC ФНЧ: R 1к, C 100н; сигнал на вх" --open
python src/mcnl/app.py --netlist схема.txt --open        (свой нетлист, без переводчика)
python src/mcnl/app.py "…" --model путь/model.py:Model    (другая батарейка)
python src/mcnl/app.py --netlist схема.txt --opamp TL071C  (на чертеже реальный ОУ с питанием)
python src/mcnl/app.py --netlist ответ.txt --mode 2       (подбор номиналов по ответу с ? и .SPEC)
```
Отчёт - JSON: ответ переводчика, ошибки разбора, канонический нетлист, f_хар, результат MC12, измерения (тип АЧХ, k, fc, f0, Q, f_u), путь к .CIR. Рабочая папка (`--out`, по умолчанию `out/app`) должна быть обычной: MC12 не видит перенаправленные папки приложения Claude.

## Демонстрация без интернета (`demo.py`)

`python src/mcnl/demo.py --out <папка>` - запрос с клавиатуры → схема в MC12 (открывается) и краткий отчёт (тип АЧХ, коэффициент передачи, fc / f0, Q); `--examples <папка>` - 10 готовых схем разных классов и файл `zaprosy.txt` с запросом к каждой. Всё локально (baseline, MC12, spice2cir). На рабочем столе автора - папка `MC12_demo`: «Запрос в схему.bat», `examples/`, `README.txt`. Папки - латиницей: MC12 - старая программа. Процесс 64-битного MC12 называется «Micro-Cap 12», 32-битного - «mc12».

## Интерфейс переводчика

Любой класс с двумя членами (базовый класс `mcnl.translators.Translator` необязателен):

```python
class Model:
    name = "qwen-lora"            # имя в отчётах
    output_format = "netlist"     # или "ir" (JSON mcnl.ir/1)

    def __init__(self, checkpoint="..."):   # загрузка весов и т.п.
        ...

    def translate(self, prompt: str) -> str:
        """Только строки элементов (V1 IN 0 DC 5 / R1 IN OUT 1k / X1 ... OPAMP_IDEAL)
        или JSON-IR; обвязку, анализы и .END добавляет программа."""
        ...

    def translate_batch(self, prompts):     # необязательно: пакетная генерация на GPU
        ...
```

Подключение: `translators.load("baseline")`, `load("mcnl.translators.baseline:RuleBaseline")` или `load("путь/model.py:Model")`; новое имя можно добавить в `translators.REGISTRY`. Программа и оценка от переводчика не зависят: замена батарейки - один параметр `--model`.

## Оценка (`evaluate.py`)

```
python src/mcnl/evaluate.py --model baseline --split test
```
Пишет `out/eval/<модель>_<выборка>/predictions.jsonl` (формат eval_spec, раздел 7), `scores.jsonl`, `summary.json`: доли S0-S4 и функциональной точности с 95% интервалом Уилсона; разбивка по уровню сложности, топологии, задаче (A / A′) и семейству формулировок. Все ответы - одним пакетом MC12; весь test (500) - около 35 с.

## Baseline на правилах (`translators/baseline.py`)

- Задача A - обратный разбор описанных элементов (тот же, что проверяет однозначность запросов генератора).
- Задача A′ - топология по названию из `data/roles_ru.json`, номиналы по ролям, сборка по `formulas.py`; каскады - по звеньям. Минимальная общая терпимость: регистр, «ё/е», виды тире, разделители «—», «=», «:» или пробел.
- Синонимы (`aliases` в словаре): названия схем («последовательный колебательный контур», «ФНЧ второго порядка на ОУ», «фильтр Рауха», «буфер»…) и обозначения ролей («Rf», «Rin», «резистор ОС», «резистор на входе», «катушка», «ёмкость»…). Обозначения перебираются от длинных к коротким; фрагмент текста, давший номинал одной роли, другой не отдаётся. Синонимы проверены примерами, написанными после составления словаря, - это проверка работы, а не оценка устойчивости.
- **baseline ошибается и молча:** распознав название схемы, он отбрасывает остальное («Повторитель на ОУ…, нагрузка 10 кОм, 100 Ом и 10 нФ» → голый повторитель). На запросах C01 так получилось в 3 ответах из 4 разобранных (human_test.md). Отказ - не единственный вид его ошибки.
- Если запрос не разобран, программа выдаёт подсказку о формате (элементы через «;» или с новой строки, роль/выводы и номинал). Это рекомендация, а не обязательный формат: обученной модели единый разделитель не нужен.
- **На синтетических выборках v1 - 100% (S0-S4, все выборки) по построению**: правила обращают шаблоны генератора. Это проверка конвейера, а не оценка понимания языка. На запросах, написанных иначе, baseline хрупок (из шести пробных «человеческих» формулировок разобрал две: «rc фнч, r=1 кОм, c=100 нФ» и шаблонную). Содержательная планка для моделей - его результат на человеческом тесте.

## Переносная версия: процессор, без Python и видеокарты (17.11.2026)

Запрос автора 17.11.2026: передать программу научному руководителю на флешке; его ПК, скорее всего, офисный - без видеокарты и без Python; «фокус на работоспособности на маломощных старых системах». Это тестовая сборка; с итоговыми адаптерами её надо будет повторить.

**Решения.**
- Модель - через llama.cpp (`llama-server.exe`, сборка b12360 = релиз v1.0.0 от 13.11.2026, вариант win-cpu-x64; в нём библиотеки под разные процессоры - от SSE4.2 и базового x64 до AVX-512, нужная выбирается сама). Программа обращается к серверу по HTTP стандартной библиотекой (`translators/llama_server.py`), torch и transformers в переносной версии не нужны. Qwen3.5 (слои Gated DeltaNet) llama.cpp поддерживает.
- Адаптеры влиты в базу (`gguf_export.py`): LoRA-файлы GGUF к базе Qwen3.5 сервер не подключает - имена тензоров слоёв DeltaNet в адаптере и в базе не совпадают («LoRA tensor 'blk.0.attn_gate.weight' does not exist in base model»). Две модели (режим 1 - `q35_4b`, режим 2 - `q35_4b_v31_m2`), сервер держит одну и перезапускается при смене режима: памяти вдвое меньше.
- Квант Q4_K_M (2,6 ГБ на модель): Q8_0 (4,2 ГБ) не точнее на запросах программы и в полтора раза медленнее (таблица ниже).
- Шаблон чата - строкой (`llama_server.chat_text`): совпал с `apply_chat_template` токенизатора на 174 запросах (программа, llm_test; инструкции v2, v3, режима 2). Запрос - `/completion`, жадный выбор токена, остановка на `<|im_end|>`.
- Прогрев: у гибридной модели сервер не может откатить состояние к общему началу запросов без контрольной точки, и инструкция (276-499 токенов) считалась заново в каждом запросе. Сервер запускается с `-cms 0 -ctxcp 4`, после загрузки и перед каждым запросом отправляется одна инструкция (`n_predict 0`): контрольная точка после неё остаётся последней и не вытесняется. Обработка запроса на i5-10300H - 8,3 -> 1,3 с; из 57 ответов программы 56 совпали с ответами без прогрева, 57-й (program-037) с прогревом стал верным.
- MC12 - копия папки без `mcap.dat`: в нём записаны пути `C:\MC12\LIBRARY\`, `C:\MC12\DATA\`; без него MC12 ищет библиотеки в своей папке (проверено: копия без `NOM.LIB` пишет «Tried Paths: …\portable_test\MC12\library\»). В реестре MC12 хранит только имя пользователя (`HKCU\Software\Spectrum Software\mc12`), другие версии Micro-Cap не задевает (ug12.pdf, «Install the program»: каждая версия - в своей папке). `mc12run.DEFAULT_EXES`: сначала MC12 рядом с программой.
- Python - копия установленного 3.12 без site-packages, тестов и документации (42 МБ, tkinter есть), запуск `pythonw -E -s` из `start.bat`: Python и переменные владельца ПК не мешают. В окне без torch по умолчанию - «Qwen3.5-4B (процессор)» (`gui.translator_choices`).
- Сборка: `python src/mcnl/portable.py` -> `out/portable/MCNL` (5,4 ГБ: модели 5,2, MC12 0,17, llama.cpp 0,05, Python 0,04); инструкция - `docs/portable_readme.txt` (в сборке README.txt). Модели: `gguf_export.py m1 …` и `m2 …` из venv-hf (исходники llama.cpp той же версии - в out/tools).

**Видеокарта (Vulkan, 18.11.2026).** В комплекте и сборка llama.cpp с Vulkan (`app/llama-vk`, b12360, та же процессорная плюс `ggml-vulkan.dll`). Замер на ноутбуке автора (12 запросов программы; ответы на всех устройствах дословно совпали с процессорной сборкой):

| устройство | медиана ответа, с | загрузка, с | смена режима, с |
|---|---|---|---|
| NVIDIA GTX 1660 Ti (Vulkan) | 1,1 | 16 | 8 |
| Intel UHD, встроенная (Vulkan) | 20,9 | 42 | 58 |
| процессор (сборка Vulkan, `-dev none`) | 7,1 | 20 | 20 |

Встроенная графика в 3 раза медленнее процессора, а сборка Vulkan грузится дольше процессорной (опрос устройств). Правило (`llama_server.pick_device`): `--list-devices` сборки Vulkan (около 1 с), первая дискретная видеокарта по имени (NVIDIA/GeForce/Quadro/RTX, Radeon RX/Pro, Intel Arc A) -> сборка Vulkan с `-dev VulkanN -ngl auto` (слоёв - сколько войдёт в память видеокарты); иначе - процессорная сборка. Не запустилась на видеокарте - процессор; на чём считает модель, окно пишет в строке состояния. Все 57 запросов на NVIDIA - 56 (ответ за 1,1 с, самый долгий 3,7 с): program-037 (длинное описание Tow-Thomas, пять точек) собран с ошибкой в одной точке. Этот запрос пограничный у квантованной модели: на процессоре без прогрева и на Q8_0 он тоже не проходил; четыре формулировки (нынешняя, «выход схемы» везде, сначала элементы, краткая запись узлами) модель на torch проходит все, GGUF - на каждом пути хотя бы одну нет. Оставлена нынешняя: на процессоре (у научрука, скорее всего, он) - 57 из 57. С адаптером v32_m1 проверить все пути заново.

Сервер привязан к программе (Job Object Windows, `llama_server.kill_with_parent`): при любом её завершении, в том числе «Снять задачу», он завершается сам - иначе остался бы процесс с моделью на 4-5 ГБ (проверено: снятый родитель - сервер исчез).

Проверено на этом ПК: сборка в чистом окружении (её Python, PATH только из system32, без torch) - модель и MC12 из комплекта, оба режима, чертёж с TL071; окно - снимками. **Не проверено:** другой ПК (Windows 10/11 без Python и Micro-Cap 12), путь с кириллицей или пробелами (MC12 - программа ANSI), SmartScreen, первый запуск MC12 на ПК без ключа реестра (возможен вопрос имени), Windows 7 (Python 3.12 его не поддерживает), Windows 8.1.

Дальше (если понадобится): сохранять состояние после прогрева на диск (`--slot-save-path`) - на старом ПК прогрев 2-4 мин при каждой загрузке; вариант Vulkan (встроенная графика Intel/AMD); замер точности GGUF на тестовых выборках - для таблицы ресурсов.
