# Спецификация датасета v2 и режима дизайнера

Дата: 2026-11-01. Статус: согласовано автором, реализация - по разделу 9.
Основа: docs/scope.md (класс и два режима), docs/generator_spec.md (генератор v1 и предложения), docs/mc12_pipeline.md (дизайнер), docs/human_test.md (запросы LLM).
Датасет v1 заморожен и не меняется; v2 - новый каталог `data/dataset/v2`, новая версия `gen-2`.

## 1. Что меняется по сравнению с v1

| Что | v1 | v2 |
|---|---|---|
| Схемы | 17 топологий и каскады | фильтры всех видов из R, L, C, ОУ; произвольные цепочки и схемы с добавками |
| Номиналы | ряды E24 / E12 | ряды и точные значения как у дизайнера |
| Запросы | шаблоны | шаблоны + парафразы LLM, короткие и небрежные записи |
| Ответы | только нетлист | нетлист или отказ с причиной |
| Проверка поведения | тип, k, fc, f0, Q | дополнительно сравнение всей АЧХ и ФЧХ |

## 2. Состав схем

### 2.1 Названные фильтры (задача A′ и описание A)

Остаются 17 топологий v1. Добавляются:

| Топология | Группа | Источник структуры | Роли |
|---|---|---|---|
| `rlc_series_lp`, выход на C | L1 | C01 (H0007), учебники | R, L, C |
| `rlc_series_hp`, выход на L | L1 | учебники | R, C, L |
| `rlc_series_bs`, выход на последовательном LC | L1 | учебники | R, L, C |
| `rc_ladder3` | L1 | C01 | R1-R3, C1-C3 |
| `lc_ladder3`, `lc_ladder5` с RS и RL | L1 | макросы дизайнера | Rs, Rl, L*, C* |
| `twin_t` | L2 | `DATA/Filters` | R1, R2, R3, C1, C2, C3 |
| `mfb_lp`, `mfb_hp` | L2 | `data/designer` | по схеме |
| `integrator`, без резистора в ОС | L2 | C01 (H0043) | R, C |
| `differentiator` | L2 | C01 | C, R |
| `tow_thomas`, `khn` | L3 | `data/designer` | по схеме |

Fleischer-Tow, Acker-Mossberg, DABP, Tow-Thomas 2 в генератор не входят: дублировать каталог дизайнера незачем. Они остаются в проверочной выборке `mc12_real`. Сумматоры и два входа - вне класса (отказ).

Для каждой топологии: `formulas.py` (нетлист по параметрам), словарь ролей и синонимов `data/roles_ru.json`, проверка `mna.py` против MC12.

### 2.2 Композиции (только задача A)

Новый модуль `compose.py`: схема без названия, собранная случайно, с ожидаемым поведением из `mna.py`.

- **Цепочка:** 2-6 секций; секция - R, L или C последовательно, R, L, C или RC на землю.
- **Добавка к схеме:** к топологии из 2.1 с вероятностью 1-3 операции: R последовательно на входе, RC на входе, R последовательно на выходе, RC на выходе, нагрузка, C параллельно ОС, повторитель на выходе, ветвь между несмежными узлами.
- **Ограничения:** не более 12 элементов и 3 ОУ у композиций; проверка, что `IN` и `OUT` соединены; без двух источников и без коротких замыканий.
- **Выход:** случайно либо «после добавки» (`OUT` сдвигается), либо «от выхода к отдельному узлу» (`OUT` остаётся). Запрос всегда называет, откуда снимать.

### 2.3 Странные, но однозначные схемы, около 10% train

Эталон - дословный. Виды: висящий элемент, интегратор без цепи по постоянному току, нереальный номинал (50 пГн, 100 ГОм), конденсатор на идеальном источнике, схема с выходом через один элемент.

### 2.4 Отказы, 4-5% train (решение автора)

```
REFUSE out_of_class: транзистор вне класса схем
REFUSE ambiguous: не указано, куда подключён C2
REFUSE needs_design: номиналы не заданы, расчёт - режим дизайнера
```
Первая строка ответа; после неё ничего. Для JSON-IR - `{"refuse": "ambiguous", "reason": "..."}`. Доли кодов примерно поровну. Источники запросов: шаблоны вне класса (диоды, транзисторы, два входа, цифровые), порча описания (убрать подключение, два противоречивых номинала), запросы по спецификации.

## 3. Номиналы

- Ряды E24/E12 - 70%; точные 4-5 цифр, как у дизайнера (`21.16k`, `8.1016n`), - 30%.
- Диапазоны - как v1 (`sampler.RANGES`).
- Новое ограничение: разброс внутри одного типа в схеме не больше 1000 раз (в v1 пять схем отсеял допуск при разбросе порядка 10^4; у DABP дизайнера - около 19).
- Для Q и частоты - отсев как в v1: f 10 Гц - 1 МГц, Q 0,5-10.

## 4. Запросы

Семейства v1 остаются. Новое:

| Что | Пример | Доля train |
|---|---|---|
| `freeform` (новые шаблоны) | «накидай RC: 10к в разрыв, 1мкФ с выхода на землю» | 20% |
| `terse` (очень коротко) | «фнч 1к 100н» | 10% |
| парафразы Claude (C02…) | переписанные шаблонные запросы | 20% |
| семейства v1 | | 50% |

Правки текста, поверх любого семейства, каждая с вероятностью 5-15%:
- кириллическая «С» в `С1`, смесь раскладок;
- «4.7» и «4,7», `10кОм` без пробела;
- GND, общий, земля, 0 В, корпус; in/out, вх/вых;
- сокращения: ОС, ОУ, ос, оу; английские названия (Sallen-Key, notch, twin-T);
- перестановка элементов, лишние фразы («нарисуй», «подпиши», питание ОУ);
- опечатка в слове, не в номинале.

Соглашения разметки (подтвердить автору):
- питание и блокировочные конденсаторы ОУ опускаются;
- «последовательно с выходом», «после выхода» - `OUT` за добавленным элементом;
- «от выхода к отдельному узлу» - `OUT` на месте;
- «выход после C» - выход с конденсатора (подтверждено автором).

Парафраза проверяется: все номиналы и подключения остались. Для шаблонов сохраняется обратный разбор; для парафраз - обратный разбор baseline недоступен, поэтому автоматическая проверка «все номиналы запроса есть в эталоне и наоборот» и выборочный просмотр автором (30 штук).

Основная форма запросов `llm_test` - без вступлений и вопросов: пользователь понимает, куда пишет. Те же схемы в исходной разговорной форме - `llm_test_chatty`, отдельная строка таблицы. В train разговорная оболочка входит малой долей, 5% парафраз (решение автора: оставить и посмотреть, как это скажется); итог - повод для v3. `llm_test` собирается так: автор получает запросы у другой модели по заданию Claude; Claude размечает, автор проверяет; схемы из него исключаются из train. В работе называется проверкой на запросах LLM, отобранных автором.

Схемы не пересекаются между выборками по `circuit_id`, как в v1. Train сбалансирован по видам фильтров; отчёт - по видам и по числу элементов (1-5, 6-10, 11-20, 20+).

## 6. Оценка: изменения в `measure.py` и `score.py`

**Сравнение кривых, новая величина `curve`.** Эталон и ответ считаются MC12 на одной сетке; `curve = max |ΔдБ| ≤ 0,1 дБ` на всей развёртке в точках, где эталон не ниже −60 дБ от максимума, и `max |Δфазы| ≤ 0,5°` там же. Формул не требует, поэтому годится для композиций и многозвенных схем. S4 v2 (`S4c`) = S3 и `curve`, `functional_c` - `curve` без требования совпадения схемы; старый S4 по `quantities` считается рядом, чтобы таблицы v1 и v2 были сравнимы. Порог проверен на 105 схемах (60 из test v1, 38 C01, 7 дизайнера), один случайный элемент изменён, MC12:

| Порог | тот же нетлист | +1% | +2% | +5% | +20% |
|---|---|---|---|---|---|
| 1 дБ / 5° (первый вариант) | 100% | 99% | 95% | 92% | 11% |
| **0,1 дБ / 0,5° (принят)** | 100% | 86% | 12% | 12% | 8% |
| 0,05 дБ / 0,2° | 100% | 20% | 10% | 11% | 6% |

Цифры - доля прошедших сравнение. Остаток при +5% и +20% - в основном элементы, почти не влияющие на кривую (висящий резистор, конденсатор на идеальном источнике), в этих случаях поведение действительно то же. Порог принимает отличие около 1%.

**Дополнительные величины для отчёта:** крутизна спада (дБ/дек), глубина режекции, неравномерность в полосе.

**Отказы.** Запрос с эталоном-отказом: верно, если ответ - отказ (код считается отдельно). Запрос со схемой: отказ - ошибка `false_refusal`. Таблица: доли `false_refusal`, `missed_refusal`, точность кода.

**Допуск H0043.** Схемы, упирающиеся в усиление ОУ, - по `curve` и прогону MC12, без сравнения с формулой по уровню.

## 7. Режим дизайнера

**Формат ответа модели `mcnl.flt/1`:**
```json
{"type": "LP", "response": "Butterworth", "style": "Sallen-Key", "order": 4, "fc": 1000, "gain_db": 0}
```
`type`: LP, HP, BP, BS, Delay. Для BP, BS - `f0`, `Q`. Необязательные поля: `style`, `ripple_db`, `gain_db`; не названо в запросе - `null`, значение ставит программа. Режим задаёт окно программы, поэтому модель получает другую системную инструкцию.

**Подключение (работа на уровне файлов):**
1. `designer.py` пишет `Active.flt` побайтово, с резервной копией.
2. Пользователь открывает Design → Active Filters и нажимает OK. Запуска дизайнера из командной строки нет: батч-файлы умеют только анализы (UG12, с. 43).
3. Программа забирает `.MAC` из `LIBRARY`, разбирает `cir2spice`, заменяет ОУ на `OPAMP_IDEAL`, проверяет схему нашей обвязкой против спецификации, переносит файл из `LIBRARY`.

Только шаг 2 требует окна. Отдельно проверить: нажатие кнопки сообщением Windows (`BM_CLICK`, стандартная библиотека `ctypes`), без скриншотов; если не выйдет - кнопку нажимает пользователь. Пока не реализуем Passive.flt и режим 1 (Fp, Fs): только режим 2.

**Данные:** 300 пар «спецификация на русском → JSON» по шаблонам и парафразам, отдельно от v2; метрики - точность по полям и полное совпадение. Обучается та же модель, ресурсы и сравнение моделей считаются на режиме перевода.
