# Режим дизайнера

Дата: 2026-11-01. Статус: путь «спецификация → схема» работает и проверен на MC12 12.2.0.5 (32 бит), разбор запросов - правилами; окно программы не сделано.
Код: `src/mcnl/designer.py`, `src/mcnl/designer_data.py`. Данные: `data/dataset/designer_v1`. Концепция двух режимов - docs/scope.md.

## Назначение

Пользователь пишет спецификацию, а не схему: «ФНЧ Баттерворта 4 порядка на 1 кГц». Модель извлекает параметры, номиналы считает сам MC12. Схема приходит от штатного дизайнера, поэтому расчёт фильтров мы не дублируем. Запрос на расчёт в произвольном режиме даёт `REFUSE needs_design` с предложением перейти сюда.

## Цепочка

```
запрос -> модель -> JSON mcnl.flt/1 -> проверка полей -> Active.flt -> диалог MC12, OK -> макрос в LIBRARY
       -> макрос переносится в папку схемы -> нетлист класса -> сверка со спецификацией -> .CIR, отчёт пользователю
```

Ответ модели:
```json
{"schema": "mcnl.flt/1", "type": "LP", "response": "Butterworth", "order": 4, "fc": 1000, "style": null, "ripple_db": null, "gain_db": null}
```
`type`: LP, HP, BP, BS. Для BP, BS вместо `fc` - `f0` и `Q`. `response`: Butterworth, Chebyshev, Inverse Chebyshev. `style`: Sallen-Key, MFB, Tow-Thomas, Fleischer-Tow, KHN, Acker-Mossberg, DABP, Tow-Thomas 2; `null` - как у дизайнера. Что не названо в запросе - `null`, значение модель не придумывает. Отказ - как в основном режиме.

## Подключение к MC12 (подтверждено проверкой 01.11.2026)

- Настройки: `Active.flt` читается при каждом открытии диалога; правка побайтовая, исходный файл возвращается после работы.
- Окно: управление сообщениями Windows через `ctypes`, скриншоты и захват окна не нужны. Код команды Design > Active Filters читается из меню окна (16100 на 32-битной версии), диалог открывается `WM_COMMAND`, нажатие OK - `WM_COMMAND IDOK` (текст кнопки локализован, поиск по подписи ненадёжен).
- Окно: на каждую схему запускается отдельный `mc12.exe` и закрывается после работы, окна пользователя не затрагиваются. Один экземпляр на серию не годится: каталог `Filter.cmp` возвращается к исходному, работающий MC12 спрашивает о перезаписи, и результаты сдвигаются между запросами. На 64-битной версии не проверено.
- Всплывшие вопросы MC12 (стандартные диалоги с кнопкой) закрываются программой и попадают в отчёт. Макрос с тем же именем на время работы убирается из LIBRARY и возвращается: иначе MC12 ждал бы ответа о замене (замечание автора).
- Результат: файл `<Т>_<Отклик>_<Стиль>_<f>_<порядок>.MAC` появляется в `C:\MC12\LIBRARY`; программа определяет его по времени записи, переносит из LIBRARY в папку схемы. `Macro Name` из Active.flt дизайнер игнорирует. `Filter.cmp`, `Filter.bin` и индексные файлы возвращаются к исходному виду.
- Проверка: подпись макроса (`Low-Pass Butterworth Sallen-Key`) сравнивается с запросом, АЧХ - узловым расчётом.

## Ограничения (подтверждено проверкой)

- **Эллиптический отклик не поддержан.** В режиме 2 диалога MC12 молча заменяет его на Butterworth, а со стилем Tow-Thomas макрос не появился. Нужен режим 1 (Fp, Fs, затухание), то есть другие поля спецификации. Отложено.
- **Bessel** - только тип Delay (RM12, с. 996). Delay не поддержан в первой версии.
- **Инверсный Чебышёв:** заданная частота не равна срезу по −3 дБ (4092 Гц при заданных 3000 Гц): это граница полосы задерживания в смысле дизайнера. Программа сообщает расхождение, значение не меняет.
- **Чебышёв:** частота задаётся по уровню неравномерности, поэтому fc по −3 дБ отличается (допуск 25%).
- **Несколько звеньев BP, BS:** дизайнер разносит звенья, f0 в отчёте - по всей АЧХ.

## Решения автора (01.11.2026)

1. Параметры показываются пользователю перед запуском дизайнера, возможно с визуализацией. Это часть графического окна, после доказательства работоспособности.
2. На каждую схему отдельный экземпляр MC12 (см. выше).
3. Механика как в произвольном режиме: на выходе .CIR с идеальным ОУ, схема открывается в MC12, рядом макрос.
4. Эллиптические фильтры не делаем.

## Модель и оценка

`designer_data.py`: 300 пар (train 200, dev 30, test 70), шаблоны и правки текста. Метрики: полное совпадение и точность по полям.

Разбор правилами: на шаблонном test 97,1%, на 30 спецификациях DeepSeek сначала 80%. Ошибки: усиление без единицы и запись «3-й порядок». После двух правок правил - 100%; правки сделаны по этим же 30 запросам, поэтому это верхняя оценка, а не независимый результат. Запросы DeepSeek довольно однородны, живые формулировки могут быть разнообразнее.

**Решение: режим дизайнера работает на правилах, отдельная модель для него не обучается.** Задача - извлечение нескольких полей из короткого текста. Если на реальных запросах правил не хватит, поля можно добавить в обучение как отдельную задачу.

## Проверка на 30 спецификациях DeepSeek через MC12

Каждая спецификация прошла весь путь: макрос построен во всех 30 случаях, ручных действий нет, зависаний нет. Сверка со спецификацией прошла 23 из 30, остальные 7:

| Запросы | Причина |
|---|---|
| 9, 22, 27 | инверсный Чебышёв с заданной схемой: дизайнер строит Sallen-Key вместо MFB и Tow-Thomas; у № 9 и 22 ещё и частота, см. ниже |
| 10, 21 | инверсный Чебышёв: срез по −3 дБ не равен заданной частоте |
| 26 | Чебышёв, 2 порядок, 0,2 дБ: частота задаёт край неравномерности, срез по −3 дБ другой (586 Гц при заданных 1000 Гц) |
| 19 | полосовой Чебышёв 8 порядка: подъём 2 дБ в полосе, запрошено 0 |

Подмены схемы программа показывает пользователю; расхождения частот - следствие определений дизайнера, а не ошибки.
