## Решения автора

- Пока только датасет v2. v1 обучаем потом и только при приемлемых результатах: если v2 окажется плохим, сравнение не понадобится.

- Обучение автор запускает и наблюдает сам в Colab: ноутбук показывает ход, график потерь и примеры ответов, материалы идут в текст работы.
- Модель может быть и крупнее: работа без интернета важна, но если крупная модель окажется заметно лучше, от неё можно отказаться.
- Для пробы конвейера взят Qwen2.5 7B: без запроса доступа и с известным поведением. Это не выбор для работы; свежие модели - перед фазой 3.

## Как устроена работа

Открыть ноутбук: https://colab.research.google.com/github/xdstk/lang.cir.spice.mc12/blob/main/colab/stage2.ipynb
Репозиторий публичный (решение автора 02.11.2026): с токеном Colab код не скачал, причину не выясняли.
Любой запуск в Colab лежит на Drive в `mcnl/<RUN>`: адаптер, `run.json`, `loss.png`, ответы. Ноутбук правится через `colab/build_notebook.py`.

```
репозиторий (GitHub) -> Colab: экспорт, обучение, ответы -> predictions.jsonl на Drive
                     -> ноутбук автора: evaluate.py --predictions -> MC12 -> таблицы
```
В Colab нет MC12, поэтому модель отвечает там, а оценка идёт локально. На Drive хранятся адаптеры LoRA, ответы и метаданные запуска.

Модель пишет ровно то, что записано в датасете: канонический нетлист с источником или `REFUSE код: причина`. Системная инструкция одна для обучения и для работы программы: `src/mcnl/training.py`.

- На 30 записях обучающей выборки через MC12: S3 28 из 29, поведение 29 из 29, отказ распознан с кодом. Модель учится, конвейер работает целиком.
- Единственная ошибка S3 - дефект данных, см. ниже.
- Время: 4,5 ч при пике памяти 11,7 ГБ; 26 с на проход батча из 2 записей. Это слишком медленно для T4. Вероятная причина: `is_bf16_supported()` возвращает «да» и при эмуляции, на T4 bf16 эмулируется. Исправлено: `native_bf16`, на T4 теперь fp16. Не подтверждено, покажет следующий запуск.

На Drive в `smoke1/adapter` после обрыва сессии остался только `adapter_model.safetensors`, без `adapter_config.json`. Причина не выяснена: скорее всего, Drive в Colab не успел выгрузить мелкие файлы. Обучение закончилось на шаге 125, поэтому `checkpoints/checkpoint-125` содержит тот же адаптер: веса того же размера. Теперь `hf_runtime.load` в таком случае берёт последнюю контрольную точку.

Повторный запуск ответов в Colab (03.11.2026, fp16): по времени записи файлов около 31-32 с на пачку из 8 запросов, то есть около 4 с на запрос против 14 с при эмуляции bf16. Ускорение генерации в 3-3,5 раза подтверждено; скорость обучения в fp16 ещё не измерена.
